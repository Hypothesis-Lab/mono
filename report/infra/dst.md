# Инфраструктура

Этот документ фиксирует архитектурные решения и текущие допущения по
инфраструктуре. Подробные расчёты нагрузки, конфигурации и стоимости приведены
в [спецификации инфраструктуры](https://docs.google.com/document/d/1FNX0RSjIb3oKiRJOM_PdzFz8eI6TVHyUu_I-0A0692A/edit?tab=t.0#heading=h.4m1nomwosxzs).

В основе системы лежит классическая **three-tier application**: presentation
tier, backend/API logic tier и data tier. К этой схеме добавлены асинхронные
процессы для фоновых задач и длительных workflow: backend workers, generator
workers, LangGraph и Temporal.

## Состав сервисов

Система состоит из нескольких независимо масштабируемых частей:

- несколько stateless-инстансов backend API за балансировщиком;
- backend worker для фоновых задач;
- generator workers для LLM-задач и обработки изображений, включая LangGraph
  для выполнения и восстановления генерационных пайплайнов;
- Temporal для длительных Saga-workflow и оркестрации зависимых операций;
- PostgreSQL для транзакционных данных и состояний задач;
- ClickHouse для аналитики и агрегатов;
- S3-хранилище для готовых изображений и других крупных артефактов;
- внешние API для LLM и image generation.

LangGraph не является отдельным сервисом: это часть generator application,
которая выполняется внутри generator workers.

## Синхронные и асинхронные операции

Синхронно backend обрабатывает короткие операции: аутентификацию, валидацию,
CRUD-запросы, постановку задачи и чтение текущего статуса.

Генерация креативов, вызовы LLM и image API, retries, выполнение LangGraph и
длительные Saga-workflow выполняются асинхронно. HTTP-запрос не удерживается на
всё время выполнения операции: backend возвращает идентификатор задачи или
workflow, а клиент позднее получает статус и результат.

Такое разделение уменьшает связанность сервисов, позволяет перезапускать и
масштабировать workers независимо от API и изолирует пользовательские запросы
от задержек внешних провайдеров.

Синхронный request-response остаётся основным для коротких операций: запрос
проходит через presentation tier, backend/API logic tier и, когда это нужно,
data tier, после чего результат или ошибка возвращаются пользователю. Ошибка не
маскируется внутри отдельного фонового процесса: клиент видит её и может
повторить операцию.

Повторный запуск безопасен там, где операция спроектирована как idempotent.
Idempotency keys, уникальные ограничения и проверка текущего состояния не дают
повторному запросу создать дубликаты или повторно применить уже выполненное
изменение. Это особенно важно на границах между API, очередью, generator и
Temporal, где запрос или сообщение может быть доставлено повторно.

Такое сочетание делает систему устойчивой к типичным временным сбоям:
перезапуску процесса, потере соединения, повторной доставке сообщения и
частичному завершению workflow. Однако idempotency сама по себе не исправляет
повреждённые данные. Для этого нужны транзакции, ограничения базы, явные
переходы статусов, checkpoints, Saga compensation и reconciliation.

## Backend API

Backend API запускается в нескольких экземплярах за балансировщиком. API не
должен хранить состояние пользовательской сессии или выполнения workflow в
локальной памяти процесса. Это позволяет:

- переживать перезапуск или обновление одного экземпляра;
- распределять запросы между экземплярами;
- масштабировать API горизонтально при росте параллельной нагрузки.

Несколько экземпляров нужны прежде всего для доступности и эксплуатационной
гибкости. Текущая оценка трафика сама по себе не доказывает необходимость
горизонтального масштабирования: фактические пределы нужно проверять
нагрузочным тестированием.

## PostgreSQL

На текущем этапе планируется один PostgreSQL instance без репликации. Внутри
одного PostgreSQL процесса backend и generator должны использовать разные
databases. Это сохраняет разделение владения данными при общей инфраструктуре.

Первый способ масштабирования PostgreSQL — вертикальный: увеличение CPU, RAM,
производительности диска и IOPS. Предварительная оценка рассчитана на 7 000
клиентов, но не является доказательством того, что одна конфигурация выдержит
7 000 одновременно активных пользователей. Это нужно проверить измерениями на
реальном железе с реалистичным профилем запросов, параллельными workflow,
записями checkpoint’ов, блокировками и нагрузкой на диск.

Один PostgreSQL остаётся single point of failure для базы. Поэтому две
инстанции backend не обеспечивают полную отказоустойчивость системы: при
недоступной базе API также не сможет выполнять операции, требующие её данных.

## Будущая отказоустойчивость базы

Позже можно добавить второй PostgreSQL instance как standby:

- primary принимает запросы и передаёт изменения standby;
- standby обычно не используется приложением для чтения;
- при отказе primary standby можно вручную или автоматически promote в primary;
- после восстановления старый primary нужно заново синхронизировать и вернуть в
  репликацию.

Такой standby улучшит доступность и позволит выполнить failover, но не заменит
резервные копии и point-in-time recovery. Ошибочное удаление или некорректное
изменение данных может быть распространено на standby вместе с остальными
изменениями.

Репликация и автоматический failover относятся к следующему этапу и не входят
в текущую оценку инфраструктуры и стоимости.

## Почему PostgreSQL, а не MongoDB

Основные данные системы имеют связи и инварианты: клиенты, продукты,
эксперименты, тесты, офферы, задачи, статусы, ownership и idempotency. Для них
важны транзакции, foreign keys, unique constraints, индексы и согласованные
переходы состояний.

LLM не делает MongoDB обязательным. Меняющиеся части результата можно хранить
в PostgreSQL через `JSONB`, а структурированные поля изменять обычными
миграциями. Поэтому преимущество MongoDB в schemaless-модели для этого проекта
не перевешивает преимущества PostgreSQL в транзакционной целостности и
связанных данных.
