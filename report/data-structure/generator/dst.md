# Схема базы данных

Генератор хранит задачи в таблице `generator.job`.

## Почему generator — отдельный микросервис

Generator выделен в отдельное приложение на Python, потому что задачи с LLM
обычно проще и естественнее разрабатывать на Python. Это мост между backend и
data science: специалисты могут работать с пайплайнами, моделями и оценкой
результатов в привычном для них языке, не меняя основной backend.

Основной микросервис написан на Go, поэтому Python generator является отдельным
приложением с собственной сборкой, зависимостями и процессом выполнения.
Подробности оркестрации через LangGraph вынесены в
[`langgraph.md`](../langgraph.md).

Backend взаимодействует с generator асинхронно: backend ставит задачу в очередь,
а generator выполняет её независимо и возвращает результат после завершения.
Это уменьшает связанность микросервисов, не удерживает HTTP-запрос во время
работы LLM и позволяет каждому сервису отдельно переживать перезапуск и
масштабирование.

Планируется также разделить базы данных сервисов на уровне PostgreSQL:
backend и generator должны использовать две разные database внутри одного
процесса PostgreSQL. Это ограничит владение данными, уменьшит связанность
миграций и позволит развивать хранилища независимо. Пока сервисы используют
одну PostgreSQL database, но generator уже размещает свои таблицы в схеме
`generator`.

## `generator.job`

| Поле | Тип | Описание |
|---|---|---|
| `id` | `UUID` | Уникальный идентификатор задачи, primary key |
| `product_id` | `TEXT` | Идентификатор продукта из backend |
| `kind` | `TEXT` | Тип пайплайна, например `audiences` или `audience_questions` |
| `input` | `JSONB` | Входные данные пайплайна |
| `status` | `TEXT` | `queued`, `running`, `failed` или `completed` |
| `retry_generation` | `INTEGER` | Номер полного повтора задачи |
| `result` | `JSONB` | Результат завершённой задачи |
| `persisted` | `BOOLEAN` | Сохранил ли backend результат у себя |
| `created_at` | `TIMESTAMPTZ` | Время создания задачи |
| `finished_at` | `TIMESTAMPTZ` | Время завершения задачи |

## Индексы и ограничения

- `id` — primary key.
- `(kind, status, created_at)` — поиск задач для worker.
- `(product_id, kind) WHERE NOT persisted` — не позволяет создать две несохранённые задачи одного типа для продукта.

# Жизненный цикл

```text
queued → running → completed → persisted
              └──→ failed → queued  (повтор)
```

# Интеграция с бэкендом

1. Backend создаёт задачу со статусом `queued`.
2. Generator worker переводит её в `running` и выполняет пайплайн.
3. При успехе сохраняются `result`, `status = completed` и `finished_at`.
4. Backend забирает завершённую задачу по `kind`.
5. После сохранения результата backend выставляет `persisted = true`.

# Пайплайн `audiences`

Пайплайн исследует продукт на группе синтетических аудиторий, оценивает их соответствие продукту и формирует гипотезы для проверки.

## Входные данные

Пайплайн получает:

- описание продукта и подтверждённые факты о нём;
- настройки эксперимента и целевое действие;
- основную метрику и критерий успеха;
- настройки кампании и доступные каналы.

## Обработка

1. Проверяется, подходит ли продукт каждой аудитории.
2. Для каждой подходящей аудитории проводится предварительное интервью.
3. После интервью формируются ответы, инсайты, боли, потребности, желания и возражения.
4. Каждая аудитория получает оценки по потребности, соответствию продукта, готовности к использованию и другим критериям.
5. Аудитории ранжируются, после чего выбираются три лучшие.
6. Для каждой выбранной аудитории формируются три гипотезы.
7. Проверяется разнообразие гипотез и формируется итоговый результат.

## Результат

Результат содержит:

- исследование и оценки по каждой аудитории;
- полный рейтинг аудиторий и выбранные три лучшие аудитории;
- по три гипотезы для каждой выбранной аудитории;
- факты и инсайты, на которых основаны гипотезы;
- предупреждения и ограничения результата;
- сведения о версии пайплайна и использованной модели.
