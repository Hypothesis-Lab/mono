# Схема базы данных

Генератор хранит задачи в таблице `generator.job`.

## `generator.job`

| Поле | Тип | Описание |
|---|---|---|
| `id` | `UUID` | Уникальный идентификатор задачи, primary key |
| `product_id` | `TEXT` | Идентификатор продукта из backend |
| `kind` | `TEXT` | Тип пайплайна, например `audiences` или `audience_questions` |
| `input` | `JSONB` | Входные данные пайплайна |
| `status` | `TEXT` | `queued`, `running`, `failed` или `completed` |
| `retry_generation` | `INTEGER` | Номер полного повтора задачи |
| `result` | `JSONB` | Результат завершённой задачи |
| `persisted` | `BOOLEAN` | Сохранил ли backend результат у себя |
| `created_at` | `TIMESTAMPTZ` | Время создания задачи |
| `finished_at` | `TIMESTAMPTZ` | Время завершения задачи |

## Индексы и ограничения

- `id` — primary key.
- `(kind, status, created_at)` — поиск задач для worker.
- `(product_id, kind) WHERE NOT persisted` — не позволяет создать две несохранённые задачи одного типа для продукта.

# Жизненный цикл

```text
queued → running → completed → persisted
              └──→ failed → queued  (повтор)
```

# Интеграция с бэкендом

1. Backend создаёт задачу со статусом `queued`.
2. Generator worker переводит её в `running` и выполняет пайплайн.
3. При успехе сохраняются `result`, `status = completed` и `finished_at`.
4. Backend забирает завершённую задачу по `kind`.
5. После сохранения результата backend выставляет `persisted = true`.

# Пайплайн `audiences`

Пайплайн исследует продукт на группе синтетических аудиторий, оценивает их соответствие продукту и формирует гипотезы для проверки.

## Входные данные

Пайплайн получает:

- описание продукта и подтверждённые факты о нём;
- настройки эксперимента и целевое действие;
- основную метрику и критерий успеха;
- настройки кампании и доступные каналы.

## Обработка

1. Проверяется, подходит ли продукт каждой аудитории.
2. Для каждой подходящей аудитории проводится предварительное интервью.
3. После интервью формируются ответы, инсайты, боли, потребности, желания и возражения.
4. Каждая аудитория получает оценки по потребности, соответствию продукта, готовности к использованию и другим критериям.
5. Аудитории ранжируются, после чего выбираются три лучшие.
6. Для каждой выбранной аудитории формируются три гипотезы.
7. Проверяется разнообразие гипотез и формируется итоговый результат.

## Результат

Результат содержит:

- исследование и оценки по каждой аудитории;
- полный рейтинг аудиторий и выбранные три лучшие аудитории;
- по три гипотезы для каждой выбранной аудитории;
- факты и инсайты, на которых основаны гипотезы;
- предупреждения и ограничения результата;
- сведения о версии пайплайна и использованной модели.

# Оркестрация через LangGraph

LangGraph используется для пайплайнов, где есть зависимости между операциями, параллельные ветки, повторные попытки и продолжение после сбоя. Это избавляет от необходимости самостоятельно писать планировщик, хранение состояния и механизм восстановления.

## Граф и узлы

- **Узел** — отдельная операция графа. Обычно он вызывает языковую модель, проверяет ответ и сохраняет результат.
- Узлы `validate_input`, `schedule` и `result` выполняют служебную работу: проверяют вход, выбирают готовые операции и собирают итог.
- Независимые операции выполняются параллельно.
- Основной поток идёт downstream по зависимостям. Цикл появляется только при исправлении невалидного ответа модели.
- Каждый пайплайн имеет собственный граф, состояние и набор операций. `kind` задачи выбирает нужный граф.

## Уровни повторных попыток

| Уровень | Поведение |
|---|---|
| Запрос к модели | `ChatOpenAI(max_retries=2)` повторяет временные ошибки провайдера. Всего допускается до трёх запросов в рамках одного вызова модели. |
| Узел | Невалидный JSON или результат запускает corrective loop. Ошибка и исходный ответ сохраняются в состоянии, затем тот же узел получает feedback. Лимит — три поколения на операцию: исходное и два исправления. |
| Задача (job) | Автоматического повтора всей задачи нет. После статуса `failed` backend может запустить её вручную; завершённые операции не выполняются заново. |
| Диспетчер | Диспетчер не содержит отдельный retry loop: он ищет задачи со статусом `queued` или `running`, захватывает advisory lock и передаёт задачу worker. Ошибка графа переводит задачу в `failed`. |

`retry_generation` в таблице job — это счётчик ручного повтора всей задачи, а не счётчик вызовов модели. Счётчики исправлений отдельных узлов хранятся в состоянии графа.

`WORKER_CONCURRENCY` ограничивает число одновременно выполняемых задач, а `GRAPH_MAX_CONCURRENCY` — число готовых операций внутри одного графа. При отсутствии свободных задач диспетчер повторяет поиск через пять секунд; завершившийся worker будит его немедленно.

## Checkpoints

- Для каждой задачи используется отдельный `thread_id`, равный `job.id`.
- В checkpoint сохраняются входные данные, завершённые операции, их результаты, контекст исправления и итоговый результат.
- Это не отдельная независимая запись на каждый узел: checkpoint хранит состояние графа и список незавершённых операций.
- После успешного шага завершённые узлы не запускаются повторно при обычном продолжении.
- Если процесс остановился во время узла, этот узел может выполниться повторно, потому что его результат ещё не был сохранён.

В production checkpoints хранятся в PostgreSQL через `PostgresSaver`. Для каждого запуска используется отдельное соединение с базой, которое одновременно удерживает advisory lock задачи. `PostgresSaver.setup()` вызывается при старте генератора и создаёт или обновляет служебные таблицы LangGraph.

## Восстановление после сбоя

Backend только ставит задачу в очередь, а генератор выполняет её независимо. Если worker или процесс генератора падает:

1. PostgreSQL освобождает advisory lock после закрытия соединения.
2. Другой worker может забрать оставшуюся задачу со статусом `running`.
3. LangGraph загружает последний checkpoint.
4. Уже завершённые операции пропускаются, а незавершённая операция продолжается.

LangGraph отвечает за состояние и продолжение графа. Приложение отвечает за очередь, блокировку задачи, worker pool, статусы job и передачу готового результата в backend.
