# Почему используется Temporal

Temporal выбран для запуска и остановки гипотезы, потому что это не короткий
HTTP-запрос, а длительный фоновый процесс. Процесс должен создать во внешней
системе Yandex Direct цепочку зависимых объектов, пережить временные ошибки и
завершиться независимо от браузера, frontend и исходного HTTP-соединения.

## Задача

Запуск гипотезы создаёт в Yandex Direct связанные объекты в определённом
порядке:

```text
campaign
  └── retargeting_list
        └── ad_group
              └── audience_target
```

Один объект требует идентификатор другого объекта. Поэтому нельзя надёжно
создать всю цепочку одним запросом к Yandex и нельзя считать операцию
завершённой после создания только первого объекта.

Остановка выполняет обратную операцию: удаляет созданные объекты в обратном
порядке зависимостей.

## Почему не HTTP-запрос

HTTP handler не должен удерживать запрос до завершения всех вызовов Yandex:

- пользователь может закрыть страницу или потерять сеть;
- frontend не должен знать порядок создания внешних объектов;
- HTTP timeout не должен отменять бизнес-операцию;
- backend может перезапуститься или быть задеплоен во время операции;
- временная ошибка Yandex не должна превращаться в потерянный запуск;
- частично созданные объекты требуют продолжения или компенсации.

API отвечает `202 Accepted` со статусом `queued` и `workflow_id`. После этого
frontend только запрашивает статус. Пользовательский запрос больше не владеет
выполнением процесса и не может сломать его закрытием страницы или повторной
отправкой формы.

## Что даёт Temporal

### Долговечное выполнение

Temporal хранит историю workflow и его состояние вне процесса backend. Если
worker перезапустился, другой worker может продолжить workflow с последней
незавершённой операции. Процесс не привязан к памяти конкретного HTTP handler.

### Повторы activity

Вызовы Yandex и изменения статусов PostgreSQL выполняются как activities. Для
них заданы timeout и retry policy:

- обновление статуса запуска или остановки — до пяти попыток;
- создание или удаление ресурса — до трёх попыток для основной операции;
- компенсационное удаление — до пяти попыток;
- временная задержка между попытками увеличивается до заданного максимума.

Повторяется именно отдельная activity, а не весь процесс создания цепочки.
Уже созданные ресурсы не должны создаваться заново без проверки.

### Оркестрация зависимостей

Workflow последовательно передаёт созданные внешние идентификаторы следующим
операциям:

1. создаёт или находит кампанию;
2. создаёт или находит список ретаргетинга;
3. создаёт или находит группу объявлений, используя кампанию;
4. создаёт или находит target, используя группу и список ретаргетинга;
5. сохраняет внешний идентификатор каждого ресурса в backend ledger;
6. помечает запуск успешным только после завершения всей цепочки.

В backend это реализовано в
[`hypothesis_launch_workflow.go`](../../../backend/internal/services/hypothesis_launch_workflow.go)
и
[`hypothesis_launch_activities.go`](../../../backend/internal/services/hypothesis_launch_activities.go).

### Saga и компенсация

PostgreSQL и Yandex Direct не участвуют в одной общей транзакции. Если первые
ресурсы уже созданы, а следующий шаг не удался, workflow выполняет
компенсацию: удаляет созданные ресурсы в обратном порядке.

Это Saga, а не атомарный rollback:

```text
создание A → создание B → ошибка C
                         ↓
             удалить B → удалить A
```

Если компенсация тоже не удалась, backend не делает вид, что всё откатилось.
Запуск получает статус `reconciliation_required`, чтобы его можно было
доработать или повторить после устранения причины.

Для остановки используется отдельный workflow. Если удаление внешних
ресурсов не удаётся после всех повторов, остановка получает статус
`requires_manual_intervention`.

## Как запуск отделён от HTTP

Запуск состоит из двух частей: транзакции в PostgreSQL и фонового стартера.

1. Backend в одной транзакции проверяет состояние гипотезы, создаёт
   `hypothesis_launch`, сохраняет план ресурсов, переводит гипотезу в
   `launching` и добавляет запись в `temporal_outbox`.
2. API возвращает `202` и `workflow_id` сразу после commit.
3. `HypothesisLaunchStarter` регулярно забирает outbox-запись через
   `FOR UPDATE SKIP LOCKED`.
4. Starter запускает Temporal workflow в task queue `hypothesis-launch`.
5. После подтверждённого запуска записи outbox присваивается статус
   `dispatched`; при ошибке старта она возвращается в `pending`.
6. Worker выполняет workflow и activities, а frontend читает статус из
   backend API.

Outbox нужен потому, что нельзя сначала зафиксировать состояние запуска в
PostgreSQL, а затем надеяться, что отдельный сетевой вызов Temporal обязательно
сработает. Если backend упал между этими действиями, outbox позволяет повторно
попробовать старт. Запись со статусом `starting`, оставшаяся более минуты,
считается зависшей и может быть забрана повторно.

Реализация стартера:

- [`hypothesis_launch_starter.go`](../../../backend/internal/services/hypothesis_launch_starter.go)
- [`hypothesis_stop_starter.go`](../../../backend/internal/services/hypothesis_stop_starter.go)
- [`hypothesislaunch/repository.go`](../../../backend/internal/repositories/hypothesislaunch/repository.go)

## Что защищено от действий пользователя

Frontend не управляет внутренними шагами workflow. Пользователь не может:

- отменить создание только потому, что закрыл страницу;
- изменить порядок объектов в уже запущенной операции;
- удалить гипотезу во время запуска или остановки;
- запустить второй параллельный launch для той же гипотезы;
- считать операцию успешной до завершения всей цепочки.

Команды запуска и остановки сами являются отдельными backend-операциями с
проверкой состояния гипотезы. Остановка не прерывает незавершённый запуск:
backend сначала возвращает конфликт, а остановка разрешена после успешного
запуска.

Это не означает, что процесс невозможно остановить на уровне инфраструктуры.
Администратор может отменить workflow, worker может быть выключен, а Yandex
может быть недоступен. В таких случаях состояние операции остаётся явным, а не
теряется вместе с HTTP-запросом.

## Идемпотентность и ограничения

Temporal повторяет activities, поэтому внешние операции должны быть безопасны
при повторном выполнении. В текущей реализации это обеспечивается несколькими
механизмами:

- перед созданием ресурс ищется в Yandex по имени и зависимостям;
- внешний идентификатор сохраняется в `hypothesis_launch_resource.external_id`;
- ресурс со статусом `created` повторно не создаётся;
- стабильный `ActivityID` строится из типа ресурса и `logical_key`;
- локальные переходы защищены проверками текущего статуса;
- повторный старт с тем же `workflow_id` распознаётся как уже запущенный.

Temporal не делает вызов Yandex exactly-once и не превращает внешнюю систему в
часть транзакции PostgreSQL. Возможны ситуации, когда Yandex уже создал объект,
а ответ потерялся. Поэтому поиск существующего объекта, сохранение внешнего
идентификатора и ручная reconciliation являются частью дизайна, а не
дополнительной оптимизацией.

Workflow-код должен оставаться детерминированным: побочные эффекты выполняются
в activities, а не непосредственно в workflow. Для изменений уже работающих
workflow используется `workflow.GetVersion`, чтобы новая версия backend не
сломала воспроизведение истории старых запусков.

## Дополнительные преимущества

- **Наблюдаемость:** у каждой операции есть `workflow_id`, статус, история и
  memo с типом операции, гипотезой и числом ресурсов.
- **Масштабирование:** несколько backend workers могут обрабатывать одну task
  queue без передачи работы через frontend.
- **Изоляция сбоев:** ошибка одного вызова Yandex не теряет весь workflow и не
  блокирует HTTP server.
- **Единый механизм для запуска и остановки:** оба процесса используют
  одинаковую модель workflow, activities, retry policy и ledger ресурсов.
- **Безопасное завершение:** backend регистрирует worker через lifecycle и
  останавливает его вместе с приложением, не создавая новые задания при
  shutdown.
- **Расширяемость:** в workflow можно добавлять timers, signals, queries и
  child workflows, если появятся отложенные действия, ручное подтверждение или
  более сложные цепочки.

## Почему не только PostgreSQL worker

Одного outbox и фонового polling достаточно, чтобы инициировать workflow, но
недостаточно для надёжного выполнения всей цепочки. Самостоятельная реализация
только на PostgreSQL потребовала бы поддерживать:

- lease и возврат зависших шагов;
- историю выполненных операций;
- retries с timeout и backoff;
- продолжение после перезапуска процесса;
- дедупликацию внешних вызовов;
- компенсацию уже выполненных шагов;
- версионирование workflow при деплое;
- поиск и диагностику зависших операций.

Temporal предоставляет большую часть этой инфраструктуры как платформу. Backend
сохраняет только бизнес-состояние, ledger внешних ресурсов, outbox и правила
компенсации.

## Решение

Temporal используется не просто как очередь фоновых задач. Он является
движком долговечного workflow для Saga, которая создаёт и при необходимости
удаляет зависимую цепочку объектов в Yandex Direct.

Главная граница ответственности:

- backend принимает команду, фиксирует намерение и план ресурсов в PostgreSQL;
- Temporal надёжно оркестрирует длительное выполнение и повторы;
- activities вызывают Yandex и обновляют ledger;
- Saga компенсирует уже выполненные внешние шаги;
- backend сообщает frontend только наблюдаемое состояние операции.

Таким образом, пользователь и frontend отвязаны от длительности, сетевых
ошибок и перезапусков фонового процесса, а результат операции не зависит от
жизни исходного HTTP-запроса.
